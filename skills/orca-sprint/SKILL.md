# Run a BMad sprint on Orca

Division of labor: **BMad owns the method** — PRD → architecture → epics/stories →
`sprint-status.yaml` → retrospective, all through its own `bmad-*` skills. **Orca owns
execution** — worktrees, branches, dispatches, supervision, merge gate. This skill is the
bridge: it never re-plans; it consumes what BMad produced and feeds workers.

Per story, two Orca tasks and two workers, matching BMad's own rule that review runs in a
fresh context with a *different* model than the dev:

```
<story-key>-dev      →  coded by the cheap fast model (e.g. deepseek-v4-flash via opencode)
<story-key>-review   ←  blocked-by dev, reviewed by the strong model (e.g. Claude Code Opus)
```

The **coordinator — never a worker — owns every `sprint-status.yaml` transition**. The
tracking file is a shared file by construction; applying the Shared-files contract lesson
means workers never touch it.

## Gates

- `_bmad-output/**/sprint-status.yaml` exists, generated by `bmad-sprint-planning` (else
  route there first — this skill refuses a hand-built tracking file).
- Stories to run are `ready-for-dev` **and their story file exists**. `backlog` stories are
  not runnable — they still need `bmad-create-story`.
- `docs/agents/setup.md` exists with `## Worker runtime` and `## Merge gate` recorded (else
  `/orca-setup`). On first use, add a `## Models` line recording the split verbatim:
  `dev=<model@runtime>, review=<model@runtime>` — the split is a project decision, not a
  per-sprint improvisation.
- Canary rule (see `/orca-orchestrate` runtimes.md, "Model reliability"): any model not yet
  proven on this project gets ONE task before fan-out. Never five unproven workers.

## Steps

1. Load the guides, then the state:
   ```bash
   orca skills get orchestration && orca skills get orca-cli
   ```
   Read `sprint-status.yaml`; collect stories in `ready-for-dev` whose story file exists.
   Confirm the sprint scope with the user in one line (default: all ready stories, at most
   3 dev workers in parallel).
2. Create the Run named after the sprint (`orca orchestration run-create`), then per story
   two Tasks: `-dev` and `-review` with `--deps '["<dev_task_id>"]'`. The `-dev` spec stays
   small: one framing line + **the path to the story file** — the worker reads the story
   where BMad wrote it; do not inline the story into the spec.
3. **Show the board before launching.** Print the task table (task id, story key, dev/review,
   deps, worktree/branch) and point the user at the Orca window — the graph/Tasks view is the
   live picture of dispatches and branches. This visibility is half the reason the bridge
   exists; do not skip it.
4. Move each dispatched story to `in-progress` (coordinator YAML edit), then dispatch the
   `-dev` workers on the recorded dev runtime/model. Supervise with the `/orca-orchestrate`
   loop (wait windows, degenerate-output screening, watchdog, abandonment door) — this skill
   does not duplicate it.
5. On a dev `succeeded`: move the story to `review`, dispatch `-review` with the story path +
   the diff scope (`gh pr diff <pr>` or the branch range) and BMad's review checklist
   (`bmad-review*` skills define what to check; the reviewer loads them fresh).
   - Review approves → apply the merge gate (CI green **and** mergeable — orchestrator
     contract), merge, mark the story `done`.
   - Review requests changes → one bounded round: re-dispatch `-dev` with the review notes
     prepended to the spec. Still failing → `failed`, escalate to the user with both reports.
6. Sprint close: every scoped story `done` or escalated. Report the final board, leave
   `sprint-status.yaml` fully reconciled (it is BMad's source of truth, not yours), and hand
   back to BMad: suggest `bmad-retrospective` — its action items seed the next
   `bmad-sprint-planning`.

## Done when

- Every scoped story reached `done` (gate passed, merged) or was escalated honestly.
- `sprint-status.yaml` matches reality line for line; the Run shows the complete dev→review DAG.
- No worker left live; merged branches cleaned per the project's setup conventions.
